# Архитектура и границы прототипа

Решения согласованы 2026-11-24. Первая поставка предназначена для Windows x64, Codex Desktop и DeepSeek Harness Desktop. Организация размещает сервисы в своей сети. Пользовательские сценарии — чтение Jira Data Center, поиск и чтение страниц Confluence Data Center. Для GitLab, Jenkins и Allure TestOps реализованы прямые подключения для чтения. Первичная проверка использует локальные имитации API. Совместимость с версиями рабочих экземпляров предстоит подтвердить. Возможность переноса на macOS и Linux сохраняется в устройстве ядра, а текущая поставка реализует транспорт и хранилище для Windows.

## Запуск и соединения

```text
Codex Desktop ──────── stdio ─── engmcp bridge ──┐
                                               ├── именованный канал ── engmcp serve ── модуль ── API сервиса
DeepSeek Harness ───── stdio ─── engmcp bridge ──┘                        │
Браузер ─────────────────────────── 127.0.0.1, сессия управления ────────┘
```

Ядро, мост и панель собраны в исполняемый файл на Go. Для входа через шлюз администратор может отдельно установить совместимый компонент. Команда `serve` владеет именованным каналом текущего пользователя, настройками, локальным аудитом и официальным Go MCP SDK. Один запуск `bridge` соответствует одной сессии MCP. Проба Harness, основной клиент и параллельный запуск Codex могут работать независимо. Клиент запускает сервер по требованию. Ярлык панели использует команду `open`, установщик — `stop` и ожидает завершения фонового процесса при обновлении. [Go SDK](https://github.com/modelcontextprotocol/go-sdk) · [Codex MCP](https://developers.openai.com/codex/mcp/) · [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/mcp/mcp-client/README.md)

Протокол управления доступен владельцу локального именованного канала. Имя включает SID пользователя и идентификатор каталога данных. Сервер задаёт явный DACL, клиент проверяет владельца канала. Для панели ярлык обменивает одноразовый секрет на сессию браузера. Все изменения требуют действующей сессии, проверки источника запроса и CSRF-токена. Профиль пользователя Windows задаёт границу доверия между локальными процессами. [Права именованных каналов](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights)

## Контракт модуля и права

Модули выпускает одна команда вместе с приложением. Контракт определён в [module.go](../internal/integration/module.go). Модуль объявляет операции, схемы аргументов, эффекты, обработчики, проверку адреса и соединения. Ядро публикует только включённые операции и проверяет разрешение при вызове, даже если у клиента закэширован старый каталог. Политика едина для обоих клиентов.

Версия 0.3.0 поддерживает по одному подключению каждого сервиса. У каждого собственный токен и список разрешённых операций. Jira и Confluence работают напрямую. При наличии компонента шлюза в панели появляется выбор режима. В Jira четыре переключателя. В Confluence можно разрешить поиск CQL и чтение страницы по ID независимо. Поиск по тексту строит текстовый запрос, готовый JQL передаётся без изменения. Обычное чтение запрашивает фиксированный набор полей, полное чтение — все доступные Jira-поля с их схемой. Учётные данные привязаны к базовому адресу, включая путь контекста. Переадресации при запросах с PAT отключены. Обращения к сервису имеют тайм-аут 30 секунд. Ответ больше 32 МиБ возвращает явную ошибку, остальные ответы передаются целиком.

Модуль читает Jira Data Center через REST API v2. Используются GET для JQL и чтения задачи, параметры `fields`, `expand`, `startAt`, `maxResults` и сохранение префикса адреса. В прямом режиме запрос отправляется к API сервиса с PAT. Во внешнем режиме перед тем же запросом общий компонент устанавливает сессию NetScaler nFactor. Названия инструментов MCP одинаковы в обоих режимах.

## GitLab, Jenkins и Allure TestOps

GitLab использует REST v4 и заголовок `PRIVATE-TOKEN`. Проверка подключения читает `/api/v4/user`. Списки проектов, merge requests и пайплайнов возвращаются как JSON-массивы. MR адресуется по внутреннему номеру проекта. [Аутентификация](https://docs.gitlab.com/api/rest/authentication/) · [Проекты](https://docs.gitlab.com/api/projects/) · [Merge requests](https://docs.gitlab.com/api/merge_requests/) · [Пайплайны](https://docs.gitlab.com/api/pipelines/)

Jenkins получает Basic Auth с именем пользователя и API-токеном при первом запросе. Проверка читает `/whoAmI/api/json` и проверяет признак анонимного пользователя. Путь каждой папки и задания строится из отдельных сегментов `/job/{имя}`. Параметр `tree` задаёт поля и диапазон коллекции. Для списка последних сборок используется коллекция `builds`; более раннюю известную сборку можно прочитать по номеру. [Авторизация клиентов](https://www.jenkins.io/doc/book/system-administration/authenticating-scripted-clients/) · [Remote Access API](https://www.jenkins.io/doc/book/using/remote-access-api/)

Allure TestOps обменивает персональный API-токен через `POST /api/uaa/oauth/token` с полями multipart `grant_type=apitoken`, `scope=openid` и `token`. Проверка читает `/api/uaa/me`. Полученный Bearer хранится в памяти с учётом `expires_in`. При 401 для кэшированного токена запрос чтения может один раз получить новый токен и повториться. Для карточек и списка выбран опубликованный контракт Report Service 4.24.1 под `/api/rs`. Перед приёмкой его маршруты сверяются со Swagger установленной версии. [Документация Qameta](https://docs.qameta.io/reference/api/) · [Контракт запусков 4.24.1](https://github.com/aeroideaservices/allure-api/blob/9702978be2a45fc15f4f35795e08b8a514276f57/docs/LaunchControllerApi.md) · [Контракт тест-кейсов](https://github.com/aeroideaservices/allure-api/blob/9702978be2a45fc15f4f35795e08b8a514276f57/docs/TestCaseControllerApi.md)

## Шлюз NetScaler

Профиль шлюза содержит HTTPS-адрес, логин, пароль и TOTP-секрет. При первом обращении к сервису в режиме шлюза родитель запускает отдельно установленный `engmcp-gateway/engmcp-gateway.exe`. Интерфейс компонента определён в [gateway_windows.go](../gateway_windows.go). Вход — один объект JSON через stdin с полями `product`, `gateway`, `user`, `password`, `seed` и `guard_dir`. Исполняемый файл получает секреты шлюза, поэтому его устанавливают из доверенного источника.

Компонент возвращает через stdout объект с массивом `cookies` для хоста продукта либо поле `error` с категорией ошибки. PAT передаётся только в API продукта. Cookies хранятся в памяти отдельно для каждого сервиса. Входы сериализованы для общего аккаунта. При истечении сессии EngMCP может повторить авторизацию и запрос один раз. Ответ 401 от самого сервиса возвращается клиенту.

## Секреты и аудит

Версионированный файл сохраняется атомарно. Секреты защищены DPAPI текущего пользователя и хранятся в зашифрованном виде в том же файле. Это позволяет сохранить смену адреса и привязку нового токена одной операцией. Панель проверяет версию формы при сохранении из нескольких вкладок. Токены и тексты задач отсутствуют в конфигурациях клиентов и локальных журналах. [Windows DPAPI](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata)

Ограничений на передачу данных задач модели пользователь не установил. Аудит остаётся локальным. Разрешённые поля событий заданы структурой, срок хранения настраивается от 1 до 3650 дней. Ротация выполняется по дням UTC и при размере файла 5 МиБ. Истечение проверяется при старте, сохранении настроек и раз в час.

## Приёмка и следующие этапы

- Прототип должен устанавливаться и обновляться под обычным Windows-пользователем. Для первого выпуска выбран неподписанный установщик Inno Setup. Специальные настройки корпоративного прокси, SSO и распространения отложены.
- Критерий для прав — после выключения операции оба подключённых клиента получают отказ, счётчик обращений к Jira остаётся прежним. Критерий для полей — сохраняются пользовательские поля, значения null и метаданные.
- Согласованы до 2 с до готовности каталога, до 80 МиБ суммарного рабочего набора сервера и двух мостов в простое и до 50 мс p95 на малом локальном ответе. Внешняя Jira измеряется отдельно. [Методика проверки](verification.md)
- При первом чтении конфигурации 0.1.0 адрес Jira, зашифрованный PAT, права и срок аудита переносятся в память как прямое подключение. Confluence выключен. При следующем сохранении панель атомарно записывает формат версии 2. При чтении настроек 0.2.0 отсутствующие модули добавляются выключенными. Сохранённые права существующих модулей загружаются из файла.
