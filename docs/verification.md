# Проверка Windows-прототипа

## Быстрые проверки и сборка

В корне репозитория запусти `go test ./...`, `go vet ./...`, затем `.\build.ps1`. Готовые файлы находятся в `dist`. Установщик включает сервер с веб-панелью и уведомления о лицензиях зависимостей. Ключ `-Go` принимает путь к go.exe, `-Iscc` — путь к компилятору Inno Setup. Сборка без установщика выполняется с ключом `-BinaryOnly`.

## Две MCP-сессии и бюджеты

`python -X utf8 tests/smoke.py` на Windows с Python 3.10+ поднимает локальную Jira-фикстуру и временный профиль EngMCP. Тест проверяет чистый каталог, конфигурирует Jira, останавливает процесс, одновременно запускает два моста и ждёт список всех инструментов в обеих сессиях. До готовности каталога счётчик запросов к Jira должен оставаться нулевым.

Далее тест читает задачи через MCP, снимает разрешение в работающем процессе и сверяет оба каталога, отказы и аудит. Замер задержки включает полный путь MCP, локальную HTTP-фикстуру и запись журналов. p95 берётся по 100 успешным чтениям. Суммарный Working Set снимается для одного сервера и двух мостов после завершения запросов. Бюджеты — 2000 мс, 80 МиБ и 50 мс соответственно.

## Движки настольных клиентов

Установи на тестовой машине оба настольных клиента. Запусти Codex Desktop, затем в PowerShell выполни команды.

```powershell
$env:ENGMCP_CODEX_EXE = Get-Process codex |
    Where-Object Path -like '*WindowsApps*app\resources\codex.exe' |
    Select-Object -First 1 -ExpandProperty Path
python -X utf8 tests/smoke.py --desktop
```

Тест создаёт временный профиль Codex и обращается к `mcpServerStatus/list` и `mcpServer/tool/call` движка из Desktop. Для DeepSeek Harness из пользовательской установки запускает `probeServer` комплектного плагина и запрашивает задачу через поставляемый с приложением MCP-клиент. Тест не требует обращения к модели. Пользовательские конфигурации клиентов не редактируются.

## Установщик и браузер

`tests/installer_ui.py` требует Chrome и Python Playwright, а также пользователя без установленного EngMCP. В одноразовом окружении Python можно выполнить:

```powershell
uv venv .venv
uv pip install --python .venv/Scripts/python.exe playwright
.venv/Scripts/python -X utf8 tests/installer_ui.py
```

Тест устанавливает сборку без повышения прав, через браузер вводит тестовый PAT, проверяет соединение, отключает операцию и повторяет установку при работающем сервере. После обновления он проверяет сохранённый PAT, права и срок хранения, затем запускает деинсталлятор. Все временные данные теста изолированы через `ENGMCP_HOME`.

## Два режима и миграция

`go test ./...` проверяет чтение настроек 0.1.0, перенос зашифрованного PAT без расшифровки при миграции и независимость прав.

`python -X utf8 tests/product_modes.py` с установленным Playwright проверяет веб-панель в Chrome, чтение Confluence через MCP, отзыв разрешений, копирование конфигураций и отсутствие тестовых секретов в настройках и журналах. На чистой установке тест ожидает пять вкладок. При отдельно установленном компоненте дополнительно проверяет профиль шлюза и независимый выбор режима для Jira и Confluence. Путь к проверяемому экземпляру передаётся через `--exe <путь к engmcp.exe>`.

## Проверка своего подключения Jira

В панели EngMCP сохрани адрес своего тестового экземпляра Jira и PAT, затем нажми «Проверить сохранённое подключение». В подключённом MCP-клиенте выполни поиск тестовой задачи, запроси её основные поля и все поля. Для примеров, отчётов об ошибках и автоматических тестов используй вымышленные задачи и адреса.

Для проверки отдельно установленного шлюза установи пакет Python `python-dotenv` и используй команду ниже. Путь к файлу реквизитов указывается явно. В профиле Jira нужны `JIRA_PAT`, `JIRA_USER`, `JIRA_PASS`, `JIRA_TOTP_SECRET`. При проверке Confluence передай `--service confluence`, адрес Confluence и отдельный `CONFLUENCE_PAT`. Общие реквизиты шлюза также можно передать в полях `MFA_USER`, `MFA_PASS`, `MFA_TOTP_SECRET`. Проверка обращается к API текущей учётной записи, выводит результат без персональных данных и удаляет временный профиль.

```powershell
.venv/Scripts/python -X utf8 tests/live_gateway.py --env C:/private/test.env --service jira --base https://jira.example.org --gateway https://mfa.example.org
```

## GitLab, Jenkins и Allure TestOps

`python -X utf8 tests/engineering_services.py` поднимает локальные HTTP-фикстуры, открывает панель в изолированном профиле и вызывает все десять операций через stdio. Тест сверяет методы, пути с контекстом, авторизацию, пагинацию, ответ MCP и журнал. Дополнительно проверяются загрузка конфигурации 0.2.0, отзыв права без сетевого вызова, привязка имени пользователя Jenkins и обновление Bearer Allure после 401. Полная сборка запускает этот тест автоматически. Для установленной копии можно передать `--exe <путь>`.

### Приёмка в рабочей сети

1. Запиши версии трёх сервисов. На вкладке каждого укажи его адрес и реквизиты, включи нужные операции и нажми «Проверить сохранённое подключение». Сверь показанную учётную запись с профилем сервиса.
2. В GitLab найди известный проект по имени, запроси список MR и открой один по внутреннему номеру. Сверь состояние пайплайна с веб-интерфейсом. Проверь вторую страницу с `per_page=1`.
3. В Jenkins прочитай список заданий внутри знакомой папки, затем сборки вложенного задания и результат конкретной сборки. Сверь номер и статус в браузере.
4. В Allure открой `/swagger-ui.html` своего экземпляра. Проверь GET-маршруты Report Service `/api/rs/launch` с параметрами `projectId`, `page`, `size`, `/api/rs/launch/{id}` и `/api/rs/testcase/{id}`. Сверь один запуск и один тест-кейс с их карточками. При расхождении зафиксируй версию, метод, шаблон пути и HTTP-статус.
5. В каждой интеграции отключи одну операцию. Проверь её исчезновение из каталога клиента и наличие записи об отказе при вызове по старому имени. В рабочем отчёте достаточно версии, операции, статуса и локального идентификатора запроса.
